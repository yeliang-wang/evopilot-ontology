# OWL 2 DL execution development checkpoint

This is an internal P2 implementation checkpoint under the [approved plan](ontology-v090-plan.md), not a full-conformance or release claim. The standalone service still reports `reasoningReady: false`: source admission, native v2 lifecycle, durable task receipts, SHACL, complete standards coverage and actual Expert journeys must be connected and accepted before that changes.

## Asserted RDF graph inspection

`reasoning.start` also accepts `task: {kind: "rdfGraph", documentId: "..."}` for one Turtle or RDF/XML document in the selected current model. The same durable request/task lifecycle, configured Java toolchain, 120-second deadline and cancellation/recovery rules apply. The existing syntax parsers emit their actual asserted graph before OWL mapping. The response identifies the exact input document and base IRI, returns N-Triples plus its byte digest, and distinguishes statement count from distinct graph triple count. Blank-node labels identify nodes only within that serialization.

This task does not resolve imports, perform inference, establish OWL 2 DL legality, create a derived view or approve semantics. RDF-valid documents can have a completed graph result even when a separate OWL legality task rejects them. All originally admitted closure metadata remains bound to the task; only the explicitly selected document contributes graph triples. Original model bytes remain unchanged. Parsing is bounded by 100,000 emitted statements and the existing 8 MiB output envelope; limit/deadline failures never return a completed partial graph. An unrelated admission failure is not evidence of invalid RDF syntax.

## Responsibility and identity

Strict TypeScript owns admission, input/digest validation, toolchain verification, single-worker lease, process deadlines/cancellation and response identity. A compiled Java process performs one formal task using OWLAPI 5.5.1, the explicitly modified HermiT `1.4.5.519+evopilot.2`, and JFact `5.0.3` for the structurally selected ALC acceleration described below. The toolchain names both engines and selection policy. It cannot read or mutate owner asset/review state. HTTP/MCP permission and project scope remain owner-service responsibilities; this internal executor is not an independently authorized business API.

The source dependency manifest records all resolved JAR names, Maven Central coordinates/URLs and SHA-256 hashes. `scripts/build-dl-worker.mjs` verifies that exact dependency directory, compiles the owned Java source, creates an isolated worker JAR, and records a private toolchain binding. Installed execution uses that JAR and dependencies, not Maven or Java source execution. The binding includes the worker source and dependency-manifest digests, installed JAR bytes and modes, and the selected Java 21 executable, libraries, configuration and release identity. The runtime is checked before each task. Dependency/license/security and published-artifact authenticity reviews remain release work; a local hash binding does not establish them.

The compatibility recipe `toolchains/owl2-dl/engine-compat.json` binds the original HermiT source archive, five exact source entries, replacement contexts and modified-source digests, plus the owned `XmlSchemaAutomata.java` digest. HermiT's object-union simplifier removes bottom operands, then can ask the newer OWLAPI to construct an empty union. The modification returns `owl:Nothing` for that case and the sole operand for a singleton; other unions use the existing factory. The three datatype modifications connect XML character/regular-language handling and correct the length-subset conversion described below. A fourth datatype modification corrects the upstream base64 decoder returning a `HEX_BINARY` tagged value: decoded base64 values retain `BASE_64_BINARY`, preserving the disjoint hexBinary/base64Binary value spaces required by [OWL 2 section 4.5](https://www.w3.org/TR/owl2-syntax/#Binary_Data), including membership, range consistency and octet-length facets. These changes apply semantic operations during engine execution, never reclassify an exception as a logical answer. The original dependency JAR remains byte-identical. The worker JAR explicitly precedes it on the classpath and contains the modified classes plus a modification notice. The installed `engine-source` directory retains the upstream source archive, recipe, owned helper and exact modified sources with the original Oxford copyright and LGPL notice; these files also participate in toolchain integrity checks. This is a modified build, not a new upstream release or completed licensing/conformance acceptance.

`STRUCTURAL_ALC_V2` selects JFact only for consistency or entailment when **every logical premise in the import closure and every query axiom** matches the following grammar: subclass, equivalent/disjoint classes, named-individual class assertions and positive object-property assertions; expressions may contain named classes, intersection/union/complement and existential/universal restrictions over ordinary named object properties. Universal/bottom object properties and inverses are excluded from this acceleration. Nonlogical annotations/declarations have no Direct Semantics effect. Every other legal DL construct or task selects HermiT, including keys, data properties/datatypes, cardinalities, identity, anonymous individuals, property characteristics/chains, projections and explanations. A query containing a non-built-in entity absent from the complete premise signature also selects HermiT. This prevents JFact fresh-individual crashes and false entailments; declarations and assertions are never added to the premise to influence the answer. Full OWL 2 DL remains the product scope; this predicate chooses an execution algorithm, not an accepted input subset.

This selection addresses a measured model-expansion failure on the required W3C ALC cases within the unchanged resource envelope. JFact cannot be a blanket replacement: its pinned source ignores key/datatype-definition premises, and its set entailment method tests axioms individually. The predicate prevents those paths from receiving such inputs and preserves joint anonymous-witness queries on HermiT. Selection occurs before engine execution, never after a failure, and does not depend on fixture names, expected answers, ontology size or a timeout retry. Results record `reasoningEngine` and `engineSelectionPolicy`; worker-side failures retain the selection when available. A parent-enforced cancellation/timeout discards partial output and therefore may have only the exact toolchain/request binding. Full standard and combination coverage must validate this combined implementation; upstream capability flags alone are insufficient.

Prepare the source with the locked Node/TypeScript workflow, resolve the exact `toolchains/owl2-dl/pom.xml` dependencies through Maven Central, and use explicit absolute locations:

```sh
node scripts/build-dl-worker.mjs \
  --dependencies /absolute/resolved/dependencies \
  --java-home /absolute/jdk-21 \
  --engine-source /absolute/verified/org.semanticweb.hermit-1.4.5.519-sources.jar \
  --parser-source /absolute/verified/owlapi-parsers-5.5.1-sources.jar \
  --output /absolute/new/private/dl-runtime
```

The output directory must be new and outside Git. Select its private `toolchain.json` and a separate private worker directory when constructing `createDLRunner`. Tests use `EVOPILOT_TEST_DL_TOOLCHAIN` and require the installed worker to match current source. No mocked reasoner or skipped missing-toolchain case counts as support. Existing native-v1 regression tests additionally require their original `EVOPILOT_TEST_NATIVE_TOOLCHAIN` binding.

## Request and formal results

The internal `ontology-dl-request/v1` envelope includes a retained request ID, exact document/import closure and a typed task. Documents contain Unicode text, its UTF-8 byte digest, document IRI, ontology/version IRIs and explicit format. Turtle and RDF/XML support native interchange; Functional Syntax supports exact structural queries, explanations and standards fixtures without introducing another mandatory business authoring format.

Tasks currently implemented by the worker are DL profile legality, consistency, arbitrary-class-expression satisfiability, axiom entailment, finite class/object-property/data-property hierarchy and equivalence projections, named-individual realization/identity, and a replayable explanation for an established entailment or inconsistency. Satisfiability uses one query axiom `SubClassOf(owl:Thing expression)` to encode the tested expression; it is not added to the premise ontology. Query ontologies cannot import dependencies.

Statuses distinguish `COMPLETED`, `ENTAILED`, `NOT_ENTAILED`, `INCONSISTENT`, `INVALID_INPUT`, `MISSING_IMPORT`, `TIMEOUT`, `CANCELLED` and `FAILED`. A failed or interrupted task has `complete: false`. Not entailed does not assert negation. Inconsistent input produces no ordinary entailment/projection result. An unsatisfiable class can coexist with a consistent ontology until an incompatible instance is asserted. Finite projections explicitly identify the requested named entities and say that they are not all logical consequences. Identity entailment does not physically merge records.

Entailment checks the complete query axiom set jointly, preserving shared anonymous witnesses; separate per-axiom results would not establish that conjunction. Empty logical conclusions are explicitly labeled `vacuous: true`. Their logical truth cannot satisfy independent business coverage requirements or missing mandatory shapes.

Results bind the exact request, original closure, effective configuration and toolchain digests. They are formal observations; owner-service persistence and actual review remain separate. The executor itself does not implement business request replay, semantic approval or delivery.

## Imports and parsing

Every import edge resolves to exactly one admitted document identity/digest. Missing, conflicting or unreachable inputs are rejected. Expected imports are parsed separately from their supplied in-memory contents; unknown loads are mapped to a non-retrievable URN. No import fetch receives its original HTTP, file or classpath address. Actual import declarations and parsed ontology/version identities must match the supplied closure, then the worker constructs a separate union of the closure's axioms for Direct Semantics.

OWLAPI 5.5.1's strict RDF reader counts import objects as ontology-header candidates and rejects a legal importing document. The adapter therefore uses the normal RDF reader with illegal-punning repair disabled, checks exact identities/imports, and runs the complete `OWL2DLProfile` check before reasoning. Reported unparsed RDF triples must be empty. The separately named consumer reconstructs nested annotations from complete typed reification groups and consumes their exact fields only when those annotation structures are attached by an actual current axiom or ontology-annotation emission. A same-valued annotation elsewhere in the ontology, a pending flush or a stale last-added axiom cannot authorize consumption. Missing typing, conflicting fields, cycles, unattached groups and foreign uses are rejected.

The [OWL 2 annotation mapping](https://www.w3.org/TR/owl2-mapping-to-rdf/#Translation_of_Annotations) permits nesting on annotations attached to ontology, axiom and annotation structures. For multiple complete reifications of one property/value pair, the consumer retains each complete nested annotation object. Structurally equal whole annotations may deduplicate; their exact source contributions remain. Distinct nested payloads are neither flattened into one object nor reduced to an arbitrary candidate. Ordinary and located parsing share this semantic correction. The input index is bounded to 200,000 unique facts, 2,000,000 references, 8,000,000 steps and nesting depth 128; ordinary parsing uses these semantic limits without allocating provenance. Parsing the premise closure, queries and explanation replay retains the original task deadline. Malformed input, timeout and resource exhaustion have distinct incomplete outcomes. Full syntax/conformance and installed native acceptance remain separate obligations.

For RDF inputs, the separate parsed projection applies the [OWL 2 RDF Mapping, Table 15](https://www.w3.org/TR/owl2-mapping-to-rdf/#Parsing_of_Class_Expressions): empty/singleton class intersections and unions, and empty individual enumerations, use their defined OWL 2 class expressions. The separately named RDF translator handles an actual `rdf:nil` intersection/union before calling OWLAPI's n-ary DataFactory, which otherwise rejects zero operands before later normalization can run. This correction does not turn a malformed nonempty list into an empty expression. Subsequent normalization traverses axiom content, preserves datatype facets and ontology annotations, and has a 256-iteration depth budget. A reflexive `owl:equivalentClass` triple, whose two positions collapse to one operand in OWLAPI's set representation, becomes an equivalent `SubClassOf(C C)` projection with its annotations retained. Functional Syntax grammar/profile checks remain unchanged. Original source documents and their hashes remain unchanged.

The RDF/XML and Turtle readers use a shared OWLAPI consumer that maps explicitly typed anonymous class expressions before axiom processing, as required by RDF Mapping section 3.2.4. The consumer first marks input complete: the upstream datatype-expression matcher needs that state to recognize qualified data cardinalities. This also maps unreferenced expressions, preventing their structural triples from becoming spurious annotations or residuals. Expressions are retained in a separate syntax-validation projection and checked with the complete import closure, including global property restrictions. That projection is never a premise, a source axiom, an explanation support or a logical conclusion: a query containing only declarations and unused expressions remains explicitly vacuous. Unmappable expressions fail rather than acquiring OWLAPI-generated error entities. Other syntax/interchange and complete standard coverage still require acceptance evidence.

RDF/XML is independently checked with a constrained SAX parser before OWLAPI parsing. External DTDs/entities and external schema access are refused; internal entity processing is bounded. Input parser errors are explicit failures. Source-level syntactic edge cases, anonymous-individual fragment stability and complete interchange round-trip evidence remain required P2 work.

The profile adapter corrects four pinned OWLAPI 5.5.1 lexical checks: `xsd:Name`, `xsd:NCName`, `xsd:NMTOKEN` and `xsd:token`. Upstream Name/NCName regex alternatives are not grouped, NMTOKEN accepts every string, and token rejects the valid empty string. A Unicode-code-point validator uses [XML 1.0 Fifth Edition name productions](https://www.w3.org/TR/xml/#NT-Name) and [XSD 1.1 string-derived datatype definitions](https://www.w3.org/TR/xmlschema11-2/#Name). Only these lexical diagnostics are replaced, and an independent traversal adds violations even when the upstream checker missed them. The same check covers premise closure, queries, nested expressions and axiom annotations; every other DL profile violation remains enforced. It never trims or rewrites literal values. Passing legality does not establish engine datatype conformance; engine value-space/facet checks are separate, and engine failures remain incomplete failures.

The separately named Functional tokenizer adapter also corrects a demonstrated upstream EOF defect: an unterminated quoted literal, a numeric token or a caret after an otherwise complete ontology could be swallowed as ordinary EOF. The adapter now distinguishes EOF while looking for a token or consuming a comment from premature EOF during token processing. Ordinary Functional premises, queries and replay documents receive the same lexical-completeness check before the unchanged OWLAPI parser; located explanations use that tokenizer directly. A quote inside a comment is still comment text. This specific correction does not establish complete syntax conformance or change valid document interpretation. Its exact modified source remains in the parser recipe and toolchain identity.

## XML character and regular-language execution

The owned Java helper implements [XSD 1.1 Appendix G](https://www.w3.org/TR/xmlschema11-2/#regexs) as regular-language automata over XML 1.0 Fifth Edition characters. It parses the XSD grammar directly, including class subtraction, Unicode categories/blocks and name-character escapes. Java or brics regular-expression syntax is not substituted for that grammar. XSD expressions match the whole string; `^` and `$` are ordinary characters. Unicode categories and blocks use the pinned Java 21 [Unicode 15.0 database](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/Character.html). Unknown well-formed block names follow XSD 1.1's default: both `\\p{IsUnknownBlock}` and `\\P{IsUnknownBlock}` denote all XML characters. Their names are retained in `unknownUnicodeBlocks`, rather than silently disappearing from diagnostics. Block matching normalizes ASCII case and separators and retains the historical Greek and combining-symbol aliases.

The HermiT adapter uses these automata for string-derived datatype value spaces and pattern facets. A supplementary character is encoded by one surrogate pair in the automaton, while character repetition and length facets count Unicode code points. The string length interval's membership and finite enumeration use the same units. Converting several string/language-tag length intervals into a pattern value space takes their union, preserving both tagged and untagged alternatives. The anyURI pattern/length adapter uses the same character units; the upstream URI base automaton remains unchanged and its complete value-space coverage remains to be verified.

Pattern facets are parsed during legality traversal of premises, queries and nested expressions, before ordinary reasoning. Invalid grammar produces `INVALID_INPUT` with `XSD_REGEX`. A valid expression that exhausts the adapter's resource envelope produces `FAILED` with `REGEX_RESOURCE_LIMIT` and `complete: false`; it never becomes a negative logical answer. Per-expression limits are 65,536 UTF-16 source units, nesting 128, repetition quantity 10,000, 50,000 states and 200,000 transitions; bounded repetition also checks quantity times operand states. Character automata are determinized/minimized before repetition to avoid quadratic surrogate-prefix expansion. The worker caches at most 16 patterns and 128 category/block sets and retains at most 128 unknown-block diagnostics. These local limits do not replace the parent deadline or establish total-process memory enforcement.

Independent source fixtures bind positive/negative membership expectations, malformed patterns, supplementary characters, character-count facets and tagged/untagged interval combinations. Tests exercise the actual installed DL engine and distinguish syntax failures from resource exhaustion. This finite coverage does not close the remaining datatype or full OWL 2 DL conformance requirements.

## Explanations and limits

The explanation task uses deterministic block deletion: it tests removing a group of logical axioms, keeps the removal only when a fresh HermiT call establishes the complete target, and otherwise divides the group. Entailment queries remain joint axiom sets, including shared anonymous witnesses; inconsistency uses its own consistency predicate. Ineligible intermediate OWL 2 DL candidates do not establish a negative answer. Engine/resource errors remain incomplete failures. All original datatype definitions stay in the reported logical support, since removing definitions can invalidate otherwise legal custom-datatype references. Nonlogical declarations and annotations stay in the replay background. Neither smallest support nor all minimal justifications is promised.

Internal search candidates carry typing declarations for the current logical candidate and complete query signature, preserving entity types when an IRI is legally punned. They add no query facts or named witnesses. The final replay retains all original nonlogical axioms, including unused declarations and annotations. Before returning `COMPLETED`, the same task serializes that replay to Functional Syntax, parses those exact returned bytes, checks the DL profile and establishes the complete target with a fresh reasoner. Search, serialization, parsing and this final check share the original deadline; there is no extra replay deadline. Results preserve the native `method: DELETION_REPLAY` contract and record `searchStrategy: BREADTH_FIRST_BLOCKS` plus `replayVerified: true`; candidate counts and retained datatype-definition counts describe the search without granting acceptance. Each supporting axiom retains its source document digest and structural selector. A structural selector alone is not a source line number, byte range or JSON Pointer.

Native explanation projections and review preparation validate these five search/replay fields as one optional group. Partial groups, an unknown strategy, a false replay claim or invalid counters are rejected. Historical evidence without that group keeps its original projection; the reader does not invent a replay verification claim or alter an earlier review report's identity. These fields describe formal execution, not a human semantic decision.

The optional [axiom source-location protocol](../specifications/v2/axiom-locations.md) preserves historical unversioned, version-1 and version-2 readers and uses version 3 for new explanations. Functional Syntax keeps its original occurrence/prefix groups. Turtle and RDF/XML use per-axiom construction and parser-context occurrence references, backed by one shared source table for each supporting document. Source fragments carry half-open UTF-8 byte ranges, raw fragment hashes and inclusive covered-character line numbers. The owner verifies their integrity against the exact retained documents; structural attribution comes from the bound worker's parser evidence. It does not independently reconstruct the RDF parser's decisions. Historical results retain their original projection shape and bytes.

This addition does not expand the business model schema: native authoring still accepts only Turtle and RDF/XML. Functional Syntax remains an internal DL/query/replay/fixture format. Version 3 requires complete source attribution across all supporting origins, including mixed imports. Premise-free support is `NOT_APPLICABLE`; missing required attribution fails rather than becoming partial success. Historical version-2 RDF/XML support retains its `UNAVAILABLE`/`PARTIAL` projection. Coverage describes the returned support, not complete product acceptance. Business-source mappings retain their declared-interpretation limits. Distribution-bound all-format native journeys remain required for EXPLAIN-03.

The RDF/XML adapter uses the existing locked Woodstox 4.1.4 semantic SAX provider after a bounded JDK security preflight on the same immutable input. The original-source scanner supplies coordinates checked against actual XML events; it does not replace SAX or construct RDF values independently. Interned source sets retain original text, CDATA, entity declaration/use and DTD default sources. Both ordinary and located parsing use the corrected grammar; ordinary parsing allocates no source collector. Derived classes are separately named, with exact upstream sources, recipes and notices retained in the worker inventory.

The applicable [RDF 1.1 XML Syntax](https://www.w3.org/TR/rdf-syntax-grammar/) normatively uses XML 1.0 Fifth Edition and Namespaces in XML 1.0. Both paths explicitly reject XML 1.1 and disable external entity/DTD retrieval. Existing caps of 1,000 entity expansions, 8 MiB total entity size and depth 256 remain enforced. The semantic provider preserves character-reference CRs in internal-entity text under [XML end-of-line handling](https://www.w3.org/TR/xml/#sec-line-ends) and [replacement-text rules](https://www.w3.org/TR/xml/#intern-replacement). This corrects the pinned JDK provider's observed conversion of such CRs to LF. The RDF grammar also corrects the upstream lowercase `rdf:statement` reification type to the normative `rdf:Statement`. Independent standard-derived expectations retain these attributed upstream differences; upstream parity alone is not the expected answer.

The development toolchain builds separately named Turtle occurrence and RDF-to-OWL mapping adapters. Exact upstream sources, patch recipes, owned helpers and modification notices accompany the worker; original dependency JARs remain unchanged. The build rejects classes that shadow locked dependency classes. Turtle 1.1 lexical parsing uses the already pinned RDF4J 5.0.2 parser, with an owned adapter retaining original UTF-16 intervals, inherited terms, generated collection/property-list triples and actual prefix/base dependencies. Ordinary and located paths use the same parser and callback implementation. Prefixes must be declared explicitly; historical implicit OWLAPI namespaces do not extend the RDF 1.1 grammar. Collection syntax emits the standard first/rest graph without additional rdf:List type triples. Blank nodes retain a bijective document-local mapping to OWLAPI's anonymous-node convention, including shared lists.

The adapter decodes IRI and string escapes exactly once from the original input, preserves numeric and typed-literal lexical forms, and independently enforces Turtle numeric-token and language-tag grammar. Invalid escapes and non-scalar values are rejected even when datatype value-space checking is deferred to a separate OWL legality task. Ordinary parsing allocates no occurrence collector, so source-table limits do not become ordinary input limits. Before public output, original intervals are converted to UTF-8 byte coordinates; shared tables retain occurrence IDs and the referenced source/context dependency closure. Regression evidence separates unchanged upstream callback parity from corrected standard behavior, including collection graphs, explicit prefixes, numeric escapes and blank-node identity. See [Turtle escape semantics](https://www.w3.org/TR/turtle/#sec-escapes).

RDF/XML additionally receives an RDF grammar check through pinned RDF4J 5.0.2 after the existing bounded XML safety preflight. This check contributes no graph values or source attribution. The same corrected OWLAPI-derived semantic grammar and Woodstox events remain responsible for ordinary/located callbacks. It supports a single node element without an rdf:RDF wrapper, empty property elements with property attributes, and the standard collection graph. Invalid RDF vocabulary positions, rdf:ID/NCName combinations and retired rdf:bagID syntax are refused before semantic callbacks. Required unqualified legacy RDF attributes (`about`, `ID`, `resource`, `parseType`, `type`) retain their RDF meanings; reserved XML attributes remain excluded from RDF property construction. These attribute rules preserve original source tokens. Datatype lexical validity remains separate from RDF syntax.

The owned `RDFIRI` helper implements the generic [RFC 3987 IRI-reference grammar](https://www.rfc-editor.org/rfc/rfc3987#section-2.2), including authority/IP literals and component-specific Unicode ranges, and the strict [RFC 3986 base-resolution algorithm](https://www.rfc-editor.org/rfc/rfc3986#section-5.2). Relative references use the current BASE; prefix bindings preserve their declaration-time resolution and its context dependencies. Raw-relative-string cache entries cannot carry an earlier BASE into a later occurrence. Empty query/fragment components remain distinct from absent components. The helper does not percent-decode, normalize Unicode, impose DNS/TLD or numerical port policy, or perform network resolution. RDF absolute IRIs require a scheme and may contain a fragment. Independent expected grammar and resolution cases accompany actual ordinary/located/native parser checks; the original parser's known cache defect is retained only as an attributed comparison. Complete distribution-bound standards evaluation remains required.

The shared RDF mapper records actual fact reads, destructive consumption, classification state, translation caches, annotation reconstruction and axiom construction. It retains the observed `rdf:nil` termination fact even though the upstream consumer omits that value from its rest map. Version 2 separates `constructionOccurrenceIds` from `parserContextOccurrenceIds`; the same occurrence may have both roles. A selection probe supplies context, while the selected cached translation retains its construction dependencies. For example, named-class shorthand handling can classify `rdf:nil` while processing an intersection and consult that classification for a later union. Those typing inputs are parser context, not additional entailment support. Neither role list is a minimal logical justification or an independently parseable RDF fragment. Normalization transfers and merges these roles to final axioms. Ordinary parsing selects the same separately named mapper with provenance disabled; independent comparisons retain the original parser.

Versions 2 and 3 bound source records at 200,000, references at 1,000,000 and unique fragment hashing at 64 MiB across the explanation. Repeated source references count against the reference budget; each original byte range is hashed once per document. XML source sets and membership edges, Turtle records and Functional fragment/context records participate in the same budget. The unchanged 8 MiB output, JSON depth 24 and 30,000-node envelope still applies and will often be reached earlier. These are refusal limits, not a promise to return 200,000 triples. The worker checks the structural output envelope before returning success; the owner checks coordinates, digests, ordering, reference closure and budgets again before projecting retained evidence.

Explanation is a separate task with a 30-second maximum deadline. Its timeout cannot turn a previously established entailment into a negative answer. Other tasks have a 120-second maximum worker deadline. Cancellation and deadline completion wait for process exit and discard partial output; the worker lease is then released.

Current frozen executor budgets: 64 documents; 8 MiB per document; 32 MiB total source text; 48 MiB request; 512 import edges; depth 16 and 8,192 traversal steps; 100,000 parsed axioms; 1,000 requested projection entities/query axioms; 8 MiB output; 64 KiB diagnostic output; JSON depth 24 and 30,000 nodes. These are worker envelopes, distinct from the smaller HTTP transport envelope. Future source-admission handlers must preserve both budgets explicitly.

The JVM has a 1 GiB heap limit, separately bounded direct memory/metadata/code cache, one active processor and Serial GC. These settings do **not** establish the plan's total-process 2 GiB memory ceiling. Actual total-process enforcement and reference-corpus resource acceptance remain P4 obligations; no heap-only measurement may close that requirement.

The [Linux cgroup development mechanism](worker-isolation-v090.md) has passed actual Java heap-bypass, Python allocation and formal-worker probes. It is not yet selected by the managed reasoner runner; installed integration and candidate resource acceptance remain required.

## Remaining acceptance

Business/regression fixtures exercise actual installed Java processes, not mocked logical results. Their fixed expectations come from the approved scenarios: sensitive classification/open-world absence, dependency chains, read-only conflicts, unsatisfiable templates, key identity, datatype values and finite projections. Import tests use an actual HTTP listener to observe zero dependency/XXE fetches. Explanation tests rerun the returned supporting ontology in a separate actual worker.

The source-checkout collector `tests/acceptance/v090/dl.mjs` executes a hash-pinned copy of the [official 2009 test archive](https://www.w3.org/2009/11/owl-test/all.rdf). Its adjacent `w3c-source.json` lock selects all 266 Approved / DIRECT / DL cases: 246 RDF/XML and 60 Functional Syntax premises, expanded into 713 legality, consistency, inconsistency, positive-entailment and negative-entailment checks. The same case can have both serializations and several checks. Expected answers come from W3C metadata. No input ontology is rewritten by the collector, and fixture imports resolve only from the archive's supplied documents.

Use the prepared native Python environment containing RDFLib for metadata extraction, the installed DL worker binding, and a new private output directory outside Git:

```sh
node tests/acceptance/v090/dl.mjs \
  --archive /absolute/private/w3c/all.rdf \
  --python /absolute/native/venv/bin/python3.12 \
  --toolchain /absolute/private/dl-runtime/toolchain.json \
  --output /absolute/private/w3c-run
```

The collector records source/artifact, archive, request, interpreter and DL toolchain identities. Each completed check has a separate immutable receipt; resuming the same output requires identical bindings and selection. `--case` and `--limit` support diagnostic subsets, which always report `INCOMPLETE`. Missing fixtures, extraction failures, invalid inputs, engine errors and timeouts count as failures, never skipped successes. A full-corpus `PASS` would cover only this W3C portion: other construct, datatype, combination, task, resource and Host requirements remain uncollected. Reports explicitly retain `productAcceptance: NOT_EVALUATED` and `fullConformanceProven: false`.

Complete W3C Direct Semantics corpus coverage, all standard constructs/datatypes and combination cases are still required, together with independent expected answers. An engine capability gap or valid-DL failure blocks release; it does not narrow the promised reasoning scope. W3C also states that passing its finite test suite alone does not prove complete conformance. See [OWL 2 conformance](https://www.w3.org/TR/owl2-conformance/) and [Direct Semantics](https://www.w3.org/TR/owl2-direct-semantics/).
