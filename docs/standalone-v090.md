# Independent Ontology development foundation

This is development implementation documentation, not a v0.9 release or installed Host acceptance record. The approved [complete plan](ontology-v090-plan.md) still requires native v2, complete OWL 2 DL, SHACL, full Expert journeys, complete operator recovery, candidate acceptance and selected historical test-asset reset.

The [language responsibility supplement](language-policy-v090.md) records the OpenHands reference and the existing TypeScript product-owner, Python RDF/SHACL and Java DL-executor division. Standards, file formats, guidance and packaging scripts are classified separately.

The internal [P2 reasoning executor](reasoning-v090.md) now has a separately installed Java worker and fixed toolchain/input identities. It is connected through explicit durable domain tasks when the operator selects an installed toolchain. Complete native-v2/conformance acceptance remains outstanding, so product readiness stays false. See the [model/task contract](../specifications/v2/models.md).

The compiled `evopilot-ontology` entry is independent of the historical `evopilot-next-ontology` CLI. `init` creates a new private workspace outside Git; it refuses occupied paths. `serve` runs a foreground loopback service with a single writer lease. `context`, `read` and `write` use that service over HTTP and never fall back to direct database mutation. Every command requires `--json`. Run the command without arguments for its exact syntax.

Operator initialization takes explicit absolute `--root` plus `--workspace`, `--project` and `--principal`. It returns identity and a private credential file location, never the token itself. The token has a 30-day expiry and one explicit project scope. The returned project scope is permitted but initially empty; actual project creation is a separate authorized owner mutation. A foreground server starts with `--root`, `--workspace`, `--service` and optional `--port`, returns its bound origin and `/mcp` URL, and stops on SIGTERM/SIGINT.

For a managed development installation, first independently install the packed package into a dedicated npm prefix outside a source checkout. `runtime-inspect --runtime-root ABS --json` records that prefix's files, digest and exact Node executable. This integrity binding does not prove published-release authenticity; download and release verification remain separate obligations. Runtime scanning admits at most 20,000 entries and 256 MiB, with only npm bin links that resolve inside the prefix.

Use `install --root ABS --workspace-root ABS --workspace ID --project ID --principal ID --runtime-root ABS --runtime-digest SHA256 --mode create --json` to prepare private installation and workspace roots. All three roots must be separate. Exact repeated setup resumes retained identity; changed inputs conflict. `--mode attach --service ID` explicitly selects an existing stopped workspace and verifies its identity, authenticated principal and permitted project. No workspace is overwritten. An interrupted workspace creation without its final identity marker requires operator recovery; it is not silently replaced.

`start --installation ABS --json`, `installation-inspect --installation ABS --json` and `stop --installation ABS --json` control the managed service. Start verifies installed bytes and the Node identity before execution, retains a unique run record, and reuses an authenticated running service. Stop authenticates the private Unix control socket and run identity; it never signals an arbitrary cached PID. Definite process death permits a new run over the retained database; an unresolved launch remains `LAUNCH_UNKNOWN`. Runs and private logs remain available for diagnosis. The initial managed-process adapter targets Unix systems; Windows service management is not established by these tests.

The CLI connection file is a private regular file with this shape (the values below are examples, not a selected installation):

```json
{
  "schema": "ontology-connection/v1",
  "origin": "http://127.0.0.1:18770",
  "workspaceId": "example",
  "serviceId": "actual-service-id",
  "projectId": "example",
  "credentialFile": "/absolute/private/location/operator-token"
}
```

The JSON endpoint is `POST /v1/request`. Standard MCP uses `POST /mcp`, implemented with the pinned official MCP SDK and both 2025 stateless and 2026 per-request protocol support. Both endpoints require a valid scoped Bearer credential, exact loopback Host, no browser Origin and uncompressed UTF-8 JSON. No remote URL or HTTP redirect may receive CLI credentials. Request bodies are bounded to 512 KiB, graph-independent JSON depth to 24 and nodes to 30,000; domain results to 1 MiB. The initial database is capped at 64 MiB, excluding its bounded transient rollback journal. The service allows at most 32 connections; rejected requests drain at most 1 MiB for at most 250 ms before closing. Invalid, oversized or interrupted exchanges are errors, never empty success. The service is local-only and is not an Internet-facing deployment.

MCP tools are `ontology_context`, `ontology_read` and `ontology_write`. Context reports actual identity, allowed projects/permissions and readiness. Read operations are `service.inspect`, `guide.read`, `project.list`, `project.inspect`, `intent.read`, `receipt.read`, `source.inspect`, `source.read` and `source.fragment.read`. Model operations additionally include `model.list`, `model.inspect`, `model.document.read`, `reasoning.list`, `reasoning.inspect` and `reasoning.result.read`. Expectation reads are `expectations.list`, `expectations.inspect` and `expectations.read`; validation reads are `validation.list`, `validation.inspect` and `validation.result.read`. Writes are `project.create`, `intent.record`, `source.admit`, `expectations.record`, `model.record`, `reasoning.start`, `reasoning.cancel`, `validation.start` and `validation.cancel`. Writes require a durable `requestId` and observed `expectedRevision`; exact replay returns its original receipt, while reuse for different content fails. Credential revocation and project permissions apply even to replay. Source bindings in intents remain declarations with `sourceVerification: NOT_EVALUATED` until separately admitted; the original intent record is never rewritten to invent collection, review or delivery.

`source.admit` takes `intentDigest` and a [native v2 source set](../specifications/v2/sources.md). All source metadata/digests must match the current intent. The service verifies actual supplied bytes and fragments, then atomically retains the immutable snapshot, its intent binding, project revision, receipt and audit. `project.inspect` exposes `sourceAdmission` with `ABSENT`, `CURRENT` or `STALE` status. Recording another intent makes the old admission stale; exact historical bytes remain readable and a prior write replay returns its original receipt without reactivating them.

`source.inspect` takes `sourceSetDigest` (or `null` for the current head) and returns metadata, typed selectors and byte spans. `source.read` takes `sourceSetDigest`, `sourceId`, `offset` and `maxBytes`; `source.fragment.read` uses `fragmentId` instead of `sourceId`. Offsets are UTF-8 bytes relative to the selected document/fragment; pages contain at most 65,536 bytes and never split a character. Continue using `nextOffset` until it is null. Every page retains original source identity and its current/stale relationship. Admission and reads remain private scoped owner operations, with no locator dereference or remote upload. The 512 KiB HTTP request budget still limits inline admission, even though the internal source contract permits larger material; a larger-material upload path is not implemented yet.

New development workspaces use explicit state version 14 for source/model/expectation snapshots and shared durable formal tasks plus immutable named views, exact review decisions and private deliveries. Prior development states v9/v10/v11/v12/v13 are rejected without mutation; no implicit upgrade or table creation occurs during service startup. Daily installation/data cutover remains deferred. Schema/version recovery is separate operator work and remains required before release.

The owner Expert source is `src/expert/SKILL.md`. Build generates the plugin Skill from those bytes; the source check rejects divergence. `guide.read` returns current first-use, modeling-intent, source-admission, expected-checks, model-draft, reasoning, validation, graph-views, explanations, evolution, semantic-review, delivery, recovery or owner-boundary guidance. The public development package contains a manifest and direct-HTTP MCP template. The installer generates a private plugin under its installation root, with a `.mcp.json` stdio entry that starts the compiled credential-file adapter. This adapter reads the current private connection and token for each request, verifies the connected service identity and forwards to the actual HTTP MCP service. It has no database fallback or installation tools and does not start the service or retry business writes. Closing the adapter leaves the separately managed service running. Its concurrency is bounded to four requests; connection/discovery deadlines are five seconds and tool calls ten seconds. No raw token is embedded in plugin configuration. The public HTTP template is an alternative that requires its own explicit endpoint and credential binding; its placeholder is not a working installation. This follows the documented [Codex plugin package and authentication format](https://developers.openai.com/api/docs/guides/agents-api/tools/plugins). Actual Codex activation and user journeys remain unverified.

Source tests use synthetic isolated projects and actual HTTP/MCP/CLI processes. The installation test packs and installs the built package into an isolated npm prefix using the local npm cache; it requires the locked dependencies to have been prepared first. These tests cover persisted intent/receipt readback, concurrent revisions, credential revocation, process death and malformed traffic. They do not establish actual Codex Host installation, business truth, complete inference or release readiness. Unknown write responses require original receipt reconciliation. A missing receipt does not authorize a new request ID or automatic retry.

The private bridge closes each stateless HTTP exchange explicitly, keeping sustained polling from reusing a socket beyond the service's 100-request budget. It never retries a domain operation automatically. Transport errors retain a bounded phase and allowlisted error codes/HTTP statuses, excluding raw error messages, response bodies, headers and credentials. A confirmed owner response remains valid if subsequent local connection cleanup fails; that cleanup failure is separately reported on stderr. After a failed status read, inspect the same task ID. After an uncertain write, read the original request receipt before deciding any next action.

Independent expectation and validation operations are described in the [native v2 expectation contract](../specifications/v2/expectations.md). `expectations.record/inspect/read/list` retain source-bound fixed requirements and cases; `validation.start/inspect/result.read/list/cancel` execute and read actual suites. `reasoning.list` discovers existing individual tasks. These operations share the same scope, revision, receipt, single queue and recovery rules. Foreground startup accepts paired `--shacl-toolchain ABS --shacl-work-root ABS` in addition to the DL pair. Both executors are required for `validationExecutionConfigured`; managed installation can retain a verified binding through the separate toolchains-bind operator command; component download/provisioning remains unfinished. A current model must bind the current expectations once they exist. A changed oracle/source/intent invalidates the former model/result binding; exact historical records stay readable.

Named graph projections use `view.record/list/inspect/read/query`, described in the [native view contract](../specifications/v2/views.md). Only `view.record` mutates state; its task IDs must identify actual completed named reasoning against the exact current model. `validation.start` may select `{kind:"derived",viewDigest}` through its optional `view` field; the owner supplies the retained component and preserves the original closure. The default is asserted. These projections add no new worker or language: TypeScript owns persistence/provenance, Java supplies actual entailments, and Python validates the explicitly selected graph.

The [native v2 lifecycle contract](../specifications/v2/lifecycle.md) defines `explanation.read`, `review.prepare/list/inspect/report.read/decide` and `delivery.record/list/inspect/export.read`. `review.decide` requires a distinct `review` permission; ordinary author credentials remain read/write only. Local operator `reviewer-grant` and `reviewer-revoke` require the service to be stopped and remain outside domain/MCP APIs. The public `@evopilot-next/ontology/native-v2` entry exports a pinned offline delivery verifier and generated types. These operations implement review/delivery source behavior; actual Host, remaining recovery and actual evolution journeys and full acceptance are still required.

The [native v2 comparison contract](../specifications/v2/comparison.md) adds read-only `model.compare.read` for exact historical/current models and selected complete validation or named-view evidence. It distinguishes source/model bytes, fixed oracle changes, actual fixed-case regressions and projection scope; it never claims semantic equivalence or complete impact. Freshness remains separate from the stable paginated report, and actual Host review must retain the comparison context.

The [managed toolchain operator](managed-toolchains-v090.md) adds `toolchains-bind` and `toolchains-inspect` for pinned, already provisioned Java/Python executors. New managed run v2 records bind the exact selection; startup verifies actual inventories and package worker identities and forwards both configurations to the owner service. Binding requires a stopped/reconciled owner and preserves exact operator receipts. Download/provisioning and actual Host acceptance remain separate unfinished obligations.

[Owned worker recovery](worker-recovery-v090.md) adds a compiled independent process supervisor and private attempt/exit journal. `task-recovery-inspect` and `task-reconcile` are separate stopped-owner commands. Confirmed exits or atomic no-launch fences can close only the original interrupted task as incomplete `FAILED`; missing evidence retains the barrier. The original business receipt remains unchanged and no task is redispatched. Supervisor-loss recovery and the hard total-process memory ceiling remain unfinished.
